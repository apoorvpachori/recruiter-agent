# Architecture decisions

Use this directory for durable choices that constrain future implementation, such as adding a datastore, introducing conversation memory, changing model/tool permissions, or exposing the API beyond loopback. Routine implementation details belong in the topic pages or code review, not an ADR.

## Record a decision

Create the next numbered file as `NNNN-short-title.md` and include:

```markdown
# NNNN. Decision title

- Status: proposed | accepted | superseded
- Date: YYYY-MM-DD

## Context
What constraint or problem requires a decision?

## Decision
What will the system do?

## Consequences
What tradeoffs, risks, and follow-up work result?
```

Keep records short and link relevant implementation and architecture pages. Do not edit an accepted record to erase history; add a new record that supersedes it, then update the current architecture pages. Never include secrets, personal profile content, or private user notes.
